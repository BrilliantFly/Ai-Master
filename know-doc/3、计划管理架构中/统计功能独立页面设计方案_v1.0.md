# 统计功能独立页面设计方案

> 版本：v1.0  
> 日期：2026-06-17  
> 范围：计划管理模块 — 统计展示重构  
> 目标：将散落在各页面的统计数据抽离为独立统计页

---

## 一、现状分析：统计信息分布散乱

目前统计数据散布在 3 个页面中，用户无法集中查看：

```
pages/plan/
├── home/index.vue      ← 今日完成/待办、月完成率、累计打卡
│                        ← 以纯数字展示，无图表
├── schedule/index.vue  ← 月历日程数，无独立统计
├── habit/index.vue     ← 进行中/已完成/累计打卡、月完成率、进度条
│                        ← 以纯数字 + 进度条展示，无图表
```

### 现有 API 支撑

| 接口 | 数据 | 使用页面 |
|------|------|---------|
| `/plan/event/today` | 今日完成/待办数 | home |
| `/plan/event/week` | 周日程事件列表 | — |
| `/plan/calendar/monthly` | 月度事件 + 习惯打卡日历 | home, habit |
| `/plan/habit/stats` | 进行中/已完成/累计打卡数 | home, habit |
| `/plan/habit/{id}/records` | 单个习惯打卡记录 | habit |

### 问题总结

1. **入口分散** — 想查统计需分别进入首页和打卡页
2. **展示单一** — 只有数字，无趋势图/柱状图/环图等可视化
3. **缺少维度** — 无按四象限的时间审计、无跨月趋势对比、无成就里程碑展示
4. **无法钻取** — 看到数字无法点击查看详情

## 四、后端新增接口

| 接口 | 方法 | 说明 | 数据来源 |
|------|:----:|------|---------|
| `/api/plan/event/quadrant-stats?year=&month=` | GET | 按四象限聚合事件数量和完成率 | `plan_schedule_event` 表 GROUP BY quadrant |
| `/api/plan/event/time-audit?range=week\|month\|year` | GET | 按象限计算时间分配占比 | `startTime` - `endTime` 差值聚合 |
| `/api/plan/habit/trend?days=30` | GET | 近 N 天每日打卡数列表 | `plan_habit_record` 按天 COUNT |
| `/api/plan/habit/rank` | GET | 按连续天数倒序的习惯排行 | `current_days` 字段排序 |

> 注：接口返回 JSON 格式，与现有 API 风格一致。

## 五、图表组件选型说明

| 组件 | 实现方式 | 依赖 | 原因 |
|------|---------|:----:|------|
| ProgressRing | SVG `circle` + `stroke-dasharray` | 无 | 环形进度条，轻量，性能好 |
| BarChart | CSS `div` + `height` 百分比 | 无 | 柱状图，直接易懂，无需 Canvas |
| PieChart | SVG 扇形路径计算 | 无 | 饼图，扇形逻辑清晰 |
| HeatmapGrid | CSS Grid + 背景色深浅 | 无 | 日历热力图，简单网格布局 |

> **零外部依赖** — 所有图表纯 CSS/SVG 实现，不引入 uCharts/ECharts 等第三方库。

## 十一、风险与注意事项

1. **时间审计精度**：现有日程数据中 `endTime` 可能不完整（旧数据缺失），需后端做默认值处理（例如未填则默认 1h）
2. **iOS/Android 图表渲染**：CSS 柱状图和 SVG 在各端兼容性良好，但需真机验证
3. **大批量历史数据**：趋势图建议限制查询范围（最多 12 个月），超过范围的引导用户按月切换
4. **首页加载速度**：原有 5 个并行请求 → 简化后仅 1 个请求，反而更快
5. **习惯里程碑**：首次打开没有打卡数据时，里程碑列表应全部显示灰色 + 提示"开始打卡解锁成就"
